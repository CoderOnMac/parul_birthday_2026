Module 9: GitHub Actions

CI/CD, workflows, and automated deployment

What is GitHub Actions?

GitHub Actions is a CI/CD (Continuous Integration/Continuous Deployment) platform that automates builds, tests, and deployments.

This Application Uses GitHub Actions The application automatically builds and deploys to GitHub Pages when you push to the main branch. No manual deployment needed.

The Workflow File

Workflows are defined in YAML files in .github/workflows/.

.github/workflows/pages.yml (lines 1-61) name: Deploy static site

on:
push:
branches: [main, master]
workflow_dispatch:

Workflow Anatomy

name

name: Deploy static site

The name of the workflow (displayed in GitHub Actions tab).

.github/workflows/pages.yml (line 1)

on (Triggers)

on:
  push:
    branches: [main, master]
  workflow_dispatch:

When the workflow runs: on push to main/master, or manually via workflow_dispatch.

.github/workflows/pages.yml (lines 3-6)

permissions

permissions:
  contents: read
  pages: write
  id-token: write

What the workflow can do: read repository contents, write to Pages, use OIDC tokens.

.github/workflows/pages.yml (lines 8-11)

concurrency

concurrency:
  group: pages
  cancel-in-progress: true

Prevents multiple deployments from running simultaneously. Cancels in-progress runs.

.github/workflows/pages.yml (lines 13-15)

jobs

jobs:
  build:
    runs-on: ubuntu-latest

Jobs are the main units of work. This workflow has a build job and a deploy job.

.github/workflows/pages.yml (lines 17-19)

steps

steps:
  - name: Checkout
    uses: actions/checkout@v4

Steps are the individual tasks within a job. Each step runs sequentially.

.github/workflows/pages.yml (lines 21-22)

Reusable actions from the GitHub Actions marketplace.

.github/workflows/pages.yml (lines 22, 25, 28)

.github/workflows/pages.yml (lines 34, 39)

The Complete Lifecycle

Viewing Workflow Runs

  1. Go to your repository on GitHub
  2. Click the "Actions" tab
  3. Click on a workflow run to see details
  4. Expand jobs and steps to see logs

Debugging Failed Workflows

  1. Find the failed step (red X)
  2. Click on the step to expand logs
  3. Read the error message
  4. Check the step before (dependency failure?)
  5. Fix the issue and push again

MCQ: Test Your Knowledge

Question 1

What is the purpose of the on section in a GitHub Actions workflow?

  • A) To define environment variables
  • B) To specify when the workflow runs
  • C) To define jobs
  • D) To set permissions

Answer: B

Explanation: The on section defines the triggers for the workflow — when it should run (e.g., on push, on pull request, on schedule, or manually).

Question 2

What is the difference between a job and a step?

  • A) Jobs run in parallel, steps run sequentially
  • B) Jobs are for deployment, steps are for building
  • C) Jobs contain steps
  • D) There is no difference

Answer: C

Explanation: A job is a collection of steps that run on the same runner. Steps are the individual tasks within a job. Jobs can run in parallel, but steps within a job run sequentially.

Question 3

What does uses: actions/checkout@v4 do?

  • A) Checks out code from the repository
  • B) Checks the Node version
  • C) Checks for errors
  • D) Checks out a branch

Answer: A

Explanation: actions/checkout@v4 is a GitHub Action that checks out your repository code onto the runner, so subsequent steps can access the files.

Interview Question

Question: What is the difference between run and uses in a GitHub Actions step?

Answer: run executes a shell command directly on the runner (e.g., run: npm install). uses specifies a reusable action from the GitHub Actions marketplace or a custom action (e.g., uses: actions/checkout@v4). run is for custom commands, while uses is for pre-built actions that handle common tasks like checkout, setup, deployment, etc.
