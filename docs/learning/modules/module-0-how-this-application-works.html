Module 0: How This Application Works

Understanding the complete lifecycle from browser to deployment

What This Application Is

This is a static web application — a birthday quiz that transforms into a love letter. It has:

  • No backend server
  • No database
  • No authentication
  • No external APIs

Everything runs in the user's browser using vanilla JavaScript.

Why This Matters Understanding that this is a static site is crucial. It means the application is simple, fast, secure, and easy to deploy. All the "logic" happens on the client side (in the browser).

The Complete Lifecycle

Here's what happens from the moment you open the URL to when the page is displayed:

User opens URL ↓ DNS Resolution (domain → IP address) ↓ Browser sends HTTP request to GitHub Pages ↓ GitHub Pages returns index.html ↓ Browser parses HTML ↓ Browser loads CSS (styles.css) ↓ Browser loads JavaScript (main.js, config.js, photoStage.js) ↓ JavaScript executes ↓ Initial state rendered (landing page) ↓ User interacts with the application

Let's break down each step:

1. DNS Resolution

When you type a URL like username.github.io, your computer needs to find the IP address of the server. DNS (Domain Name System) translates the human-readable domain into an IP address.

2. HTTP Request

Your browser sends an HTTP GET request to the server at that IP address. The request looks something like:

GET /parul_birthday_2026/ HTTP/1.1
Host: username.github.io

3. Server Response

GitHub Pages receives the request and returns the index.html file. The response includes headers and the HTML content.

4. HTML Parsing

The browser reads the HTML and builds the DOM (Document Object Model). It also discovers linked resources:

index.html (lines 28) <script type="module" src="/src/main.js"></script>

5. Resource Loading

The browser loads the linked resources:

  • CSS from src/styles.css (imported by main.js)
  • JavaScript modules: main.js, config.js, photoStage.js
  • Images (loaded dynamically by JavaScript)

6. JavaScript Execution

The browser executes the JavaScript modules. This is where the application comes to life:

src/main.js (lines 404-413) applyDocumentMeta();
render();

7. Initial Render

The render() function creates the initial HTML for the landing page and inserts it into the DOM.

How HTML, CSS, and JavaScript Interact

This application uses a clean separation of concerns:

HTML Provides Structure

The HTML in index.html is minimal — just containers:

index.html (lines 24-27) <div id="photo-stage" class="photo-stage"></div>
<div id="app" class="app">
<p class="boot-fallback">One moment…</p>
</div>

CSS Provides Styling

CSS in src/styles.css defines how everything looks:

src/styles.css (lines 2-22) :root {
--bg: #f7f4f1;
--text: #1a1816;
--accent: #c4a098;
/* ... */
}

JavaScript Provides Logic

JavaScript in src/main.js manages state and renders content:

src/main.js (lines 21-27) const state = {
phase: "landing",
questionIndex: 0,
answersLocked: false,
// ...
};
The Flow HTML defines containers → CSS styles them → JavaScript fills them with content and handles interactions

How State Is Maintained

The application uses a simple state object:

src/main.js (lines 21-27) const state = {
phase: "landing", // Current phase
questionIndex: 0, // Which question
answersLocked: false, // Can user answer?
surpriseStep: 0, // Surprise line number
revealStep: 0, // Reveal step number
};

When the user interacts, the state changes, and the render() function updates the DOM based on the new state.

Important: State Is Not Persisted If the user refreshes the page, they start over. This is intentional for this particular application. No localStorage, no cookies, no server-side session.

How User Interactions Trigger Code

Here's the flow when a user clicks the "Let's see →" button:

User clicks button ↓ Browser emits 'click' event ↓ Event listener detects the click ↓ startGame() function is called ↓ State is updated (phase: "question") ↓ render() function is called ↓ New HTML is generated for question phase ↓ DOM is updated ↓ Browser repaints ↓ User sees the question
src/main.js (lines 140-145) function startGame() {
state.phase = "question";
state.questionIndex = 0;
state.answersLocked = false;
render();
}

How the Build Process Works

When you run npm run build, Vite transforms your source files:

Source files (src/) ↓ Vite processes files ↓ Bundles JavaScript modules ↓ Minifies CSS and JavaScript ↓ Adds hashes to filenames (cache busting) ↓ Outputs to dist/ ↓ dist/ is deployed to GitHub Pages

What Vite does:

  • Bundles ES modules into a single file
  • Optimizes assets
  • Generates source maps for debugging
  • Adds hashes to filenames (e.g., index-abc123.js) for browser caching
Try It Yourself Run npm run build and look at the dist/ directory. Notice how the filenames have hashes. This is for cache busting — when you deploy a new version, browsers will download the new files instead of using cached versions.

How GitHub Pages Deploys

The deployment is automated via GitHub Actions:

Developer pushes to GitHub ↓ GitHub Actions workflow triggers ↓ Workflow runs on GitHub runner (ubuntu-latest) ↓ Checkout code ↓ Setup Node.js (v20) ↓ npm ci (install dependencies) ↓ npm run build (with BASE_PATH) ↓ dist/ is uploaded as artifact ↓ GitHub Pages deploys the artifact ↓ Available at username.github.io/repo-name/
.github/workflows/pages.yml (lines 1-61) The workflow file defines this entire process. It runs automatically whenever you push to the main branch.

Key Architectural Decisions

Why Vanilla JavaScript?

No framework overhead, smaller bundle size, easier to understand for beginners, minimal tooling required.

Why Vite?

Fast HMR (Hot Module Replacement) for instant updates during development, modern ES module support, automatic optimization.

Why GitHub Pages?

Free hosting, automatic deployment via Git, CDN-backed, HTTPS by default.

Why State-Driven Rendering?

Predictable (state is the single source of truth), debuggable (easy to see what phase the app is in), testable (can test state transitions).
